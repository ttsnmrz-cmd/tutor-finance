# Payment rollout

Use this release sequence to keep stale browser tabs from creating duplicate payments.

1. Verify the last known good artifact and exercise both payment entry points in a test environment. Inventory all writers to payments, including older tabs and any integrations. Confirm that each supported writer supplies a stable operation UUID. Check that authenticated users cannot write someone else's payments.
2. Apply the additive payment migration and release the matching notification handler during an approved maintenance window. The compatibility default means existing direct inserts still work at this point. Prepare the migration and server guard together in one release transaction, or enforce a database-side pause on payment inserts until the guard is active. A UI-only maintenance banner cannot stop a stale tab.
3. Before reopening payments, apply a separately reviewed server guard in a single transaction. Drop the automatic operation UUID default and reject INSERT when operation_id is null (for example, a BEFORE INSERT trigger instructing users to reload the app). Preserve historical nulls and their ability to be read, edited or removed under existing rules. The new RPC always supplies a UUID. A cache-busting reload and client-version message can improve the experience, but the database must enforce the requirement regardless of tab age or URL. If any supported integration cannot send a stable key, postpone the cutover and keep the current artifact.
4. Publish the matching frontend. Confirm via a deliberately stale test tab that direct POST without an operation UUID is rejected before any write. Verify same-key replay, concurrent submissions, intentional identical payments with two keys and a stale tab with an expired session. Confirm that balance updates and notification handling remain separate.
5. If the frontend needs rollback, keep the server guard, operation IDs and notification claims. Restore a known-good build that already uses the keyed RPC. If none is available, pause payment creation and repair forward. Reopening the legacy direct-write path would reintroduce the duplicate risk.

Shared recovery applies across same-origin tabs in the same browser profile. Private profiles, another browser/device, cleared site data and different origins have separate storage. The server deduplicates by supplied UUID, not by amount or date. Never reconstruct uncertain payments by starting one in another profile or device. Keep the original browser storage and reconcile in payment history. Browsers without Web Locks or storage fail closed before submitting a new payment. Telegram claims remain retained on ambiguous delivery or bookkeeping failure; check those cases manually before considering any resend.
